# Documented Anti-Patterns in Agent Memory / Context Management, and How Major Frameworks Define Memory Tiers

---

# Part A — Anti-patterns (documented, with measured penalties)

**A1. Context stuffing / naive full-context.** Zep's LongMemEval run: full **~115k-token** input scored **55.4% / 60.2%** (gpt-4o-mini / gpt-4o) at **31.3s / 28.9s**, vs **63.8% / 71.2%** at **3.20s / 2.58s** over **1.6k tokens** ([arXiv 2501.13956](https://arxiv.org/abs/2501.13956)). Mem0's full-context baseline (**26,031 tokens**) scored **highest** on LOCOMO — **72.90% ± 0.19** vs Mem0's **66.88% ± 0.15** — but at **p95 17.117s** vs **1.440s** on **1,764 tokens**, the source of its "91% lower p95 latency, >90% token savings" claim ([arXiv 2504.19413](https://arxiv.org/abs/2504.19413)). Chroma's *Context Rot* (18 models): "**significantly higher performance on focused prompts compared to full prompts**" (**~300** relevant tokens vs **~113k** full input), and **even a single distractor** drops performance below a needle-only baseline ([Chroma](https://www.trychroma.com/research/context-rot)). Anthropic frames context as a "finite resource with diminishing marginal returns" under an "attention budget" ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Positionally, **"lost in the middle"**: accuracy is "highest when relevant information occurs at the beginning or end... and significantly degrades" in the middle ([arXiv 2307.03172](https://arxiv.org/abs/2307.03172)) — where retrieved memories land.

**A2. Lossy and recursive summarization.** MemGPT's fixed-context baselines saw "a **lossy summarization** of the past five conversations to mimic an extended recursive summarization procedure" and scored **35.3%** on Deep Memory Retrieval vs MemGPT's **93.4%** — a lossy-summarization baseline, *not* a measured recursive-summarization result ([arXiv 2310.08560](https://arxiv.org/abs/2310.08560)). Letta: "**older messages have progressively less influence on the summary than recent messages**" ([Letta](https://www.letta.com/blog/agent-memory/)). LangGraph concedes trimming means "**you may lose information**," then prescribes "**Extend the summary** by taking into account the new messages above" ([LangGraph docs](https://github.com/langchain-ai/langgraph/blob/f8c1a323cc50a6da14836ebc4c53c79db0f6508c/docs/docs/how-tos/memory/add-memory.md)). Anthropic: "**overly aggressive compaction can result in the loss of subtle but critical context whose importance only becomes apparent later**" ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). [EXTRAPOLATION] I found **no peer-reviewed measurement of summary-of-summary drift**; the only figure is non-peer-reviewed — "recursive summary baseline after 5 passes: **53.4%**" ([hermes-agent#36099](https://github.com/NousResearch/hermes-agent/pull/36099)).

**A3. Model summaries as source of truth.** Graphiti: episodes are "**the ground truth stream. Every derived fact traces back here**" ([Graphiti README](https://github.com/getzep/graphiti)). Letta keeps state persisted "so they are **never lost, even once evicted from the context window**" ([Letta docs](https://docs.letta.com/agent-sdk/memory/)). LangMem says to skip a memory layer "**if that store is the source of truth** (rather than the interactions themselves)" ([LangChain](https://www.langchain.com/blog/langmem-sdk-launch)). [EXTRAPOLATION] None says "memory is a cache," but the composite rule is that derived memory must be reconstructible from an authoritative raw log — which recursive summarization destroys.

**A4. Unbounded accumulation and re-injection.** Mem0: full context forces reasoning through "mountains of irrelevant information," with preferences "buried among thousands of tokens," while attention "degrade[s] over distant tokens" ([arXiv 2504.19413](https://arxiv.org/abs/2504.19413)). LangGraph: "most LLMs still perform poorly over long contexts. They get **'distracted' by stale or off-topic content**" ([LangGraph](https://docs.langchain.com/oss/python/langgraph/memory)). Anthropic: past 200k tokens the context **truncates**, so its lead agent persists its plan externally ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)).

**A5. Memory bloat, dedup and conflict-resolution failures** — all open, reproducible bug reports:

- **Dedup fails at scale.** `mem0-ts` `add()` hardcodes the pre-extraction search to **top-10 with no similarity threshold**, so near-duplicates outside that window "are never shown to the LLM for its ADD/UPDATE/DELETE/NONE decision — and get stored as fresh duplicates" — "**8 near-identical memories about a single fact in ~1 hour**" ([mem0#7123](https://github.com/mem0ai/mem0/issues/7123)). Another measured "**13 memories stored instead of 5. The LLM-level dedup caught only 2 of 10 duplicates (20%)**" plus "**Search quality degradation**: duplicates crowd out unique facts from top-k results" ([mem0#5850](https://github.com/mem0ai/mem0/issues/5850)). [EXTRAPOLATION] No formal benchmark of retrieval precision/recall vs store size exists; evidence here is issue-tracker-grade.
- **Graph dedup/rerank failures.** Graphiti's bulk path writes two edges for one fact and mutates provenance so "**provenance is wrong on both surviving edges**" ([graphiti#1872](https://github.com/getzep/graphiti/issues/1872)); a reranker "**drops distinct edges with identical fact text**" ([graphiti#1816](https://github.com/getzep/graphiti/issues/1816)).
- **Representation bloat beyond the raw data.** Mem0 claims Zep's graph consumes "**in excess of 600k tokens**" per conversation against **26k** for the raw conversation ([arXiv 2504.19413](https://arxiv.org/abs/2504.19413)) — **vendor-vs-vendor**.
- **Framework acknowledgment.** Letta ships `/doctor` to audit memory that "has drifted or grown too large" for "placement, duplication, and system-prompt token usage," and names the **"Anti-pattern: Multiple agents doing `memory_rethink` on the same block simultaneously leads to lost updates"** ([Letta](https://docs.letta.com/configuration/memory), [shared memory](https://docs.letta.com/v1-sdk/memory/shared-memory)).

**A6. Staleness, contradictions, and delete-doesn't-delete.** Against Mem0: "**contradictory memories accumulate over time instead of the newer fact superseding the older one**," because "the scoring signals don't incorporate recency" ([mem0#4956](https://github.com/mem0ai/mem0/issues/4956)); a delete that "returns a success response, but the memory still appears in search results... **indicating no actual deletion occurred**" ([mem0#5066](https://github.com/mem0ai/mem0/issues/5066)). Against Graphiti, a measured report finds "**1 of 9 replicates correct**": "**temporal invalidation silently underperforms... stale facts survive their own contradiction**" ([graphiti#1666](https://github.com/getzep/graphiti/issues/1666)) — and since invalidation "**consistently prioritizes new information**" ([arXiv 2501.13956](https://arxiv.org/abs/2501.13956)), a wrong new fact can kill a right old one. Mem0 also reports that after writing into Zep, "**immediate memory retrieval attempts often failed... re-running identical searches after a delay of several hours yielded considerably better results**" ([arXiv 2504.19413](https://arxiv.org/abs/2504.19413), competitor measurement).

**A7. Over-retrieval and irrelevant injection.** Chroma finds distractor impact "**non-uniform**... with regards to how distracting they are relative to each other," **amplifying with input length** ([Chroma](https://www.trychroma.com/research/context-rot)). RAGGED (ICML 2025): "**some readers benefit from increased retrieval depth, while others degrade due to their sensitivity to distracting content**" ([arXiv 2403.09040](https://arxiv.org/abs/2403.09040)). Anthropic warns of "**context pollution**" at any window size and prescribes "**the smallest possible set of high-signal tokens**" ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). **Counter-evidence:** Anthropic's Contextual Retrieval found the opposite for its setup — "**using 20 [chunks] to be the most performant**" ([Anthropic](https://www.anthropic.com/engineering/contextual-retrieval)) — so over-retrieval harm is reader- and task-dependent. Over-eager *writing* costs latency: Mem0 measured **LangMem's hot-path extraction at p50 17.99s / p95 59.82s search latency**, "impractical for interactive applications" ([arXiv 2504.19413](https://arxiv.org/abs/2504.19413)).

**A8. RAG failure modes that carry over.** Deakin's experience report derives seven failure points from three case studies (BioASQ: 4,017 documents): **FP1 Missing Content, FP2 Missed the Top Ranked Documents, FP3 Not in Context (consolidation limits), FP4 Not Extracted ("too much noise or contradicting information in the context"), FP5 Wrong Format, FP6 Incorrect Specificity, FP7 Incomplete** ([arXiv 2401.05856](https://arxiv.org/abs/2401.05856)). FP2/FP3/FP4 map onto memory retrieval, context budgeting, and contradictory memories. The paper also notes chunking tradeoffs ("chunks... too long... include generated noise") and that changing embedding models forces full re-indexing. Anthropic's counter-move is refusing pre-computation: just-in-time `glob`/`grep` retrieval "**effectively bypassing the issues of stale indexing**," though runtime exploration is slower ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). For a credible-lab "RAG is not enough" stance, Microsoft Research's **Mnemis** (ACL 2026) argues "**RAG and Graph-RAG primarily retrieve memory through similarity-based mechanisms... such System-1-style retrieval struggles with scenarios that require global reasoning**" ([Microsoft/Mnemis](https://github.com/microsoft/Mnemis), [arXiv 2602.15313](https://arxiv.org/abs/2602.15313)).

**A9. Anthropic's own multi-agent caveat.** "Some domains that require all agents to share the same context or involve many dependencies between agents **are not a good fit for multi-agent systems today. For instance, most coding tasks involve fewer truly parallelizable tasks than research**, and LLM agents are not yet great at coordinating and delegating to other agents in real time." Cost: agents use "**4× more tokens** than chat interactions," multi-agent "**15×**." Observed failures: spawning **50 subagents for simple queries**, duplicated work, "distracting each other with excessive updates" ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)).

**A10. Source-reliability flags.** Mem0's paper reports Zep at **65.99%** on LoCoMo; Zep's rebuttal claims Mem0's Zep integration was wrong (wrong user model; timestamps appended to messages instead of `created_at`) and reports **75.14% ± 0.17** ([Zep](https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)). Mem0's CTO then showed Zep's originally claimed **84%** double-counted an excluded category, and that re-running Zep's own code yields "**58.44% ± 0.20**" ([getzep/zep-papers#5](https://github.com/getzep/zep-papers/issues/5)). Four numbers, one system, one benchmark — treat every Part A figure as directional. Zep's LoCoMo critique holds regardless: 26k-token conversations fit modern windows and it "**lacks questions designed to test knowledge updates**." [langmem#180](https://github.com/langchain-ai/langmem/issues/180) reviews LangMem's write path but is **authored by a competing vendor** (Mnemoverse.AI), nothing executed. Excluded as low-quality: vendor dev.to posts, emergentmind topic pages, Substack/gist lists, and a widely cited issue (`mem0ai/mem0#5352`) that **404s**.

# Part B — How major frameworks define memory tiers

The table carries each framework's tiers, write/read paths and invalidation mechanics; these notes cover what does not fit a cell.

**MemGPT / Letta.** The paper splits **main context** ("analogous to main memory/physical memory/RAM") from **external context** ("analogous to disk memory/disk storage"): main = **system instructions** + **working context** ("a fixed-size read/write block of unstructured text, writeable only via MemGPT function calls") + the **FIFO queue**; external = **recall storage** ("the MemGPT message database") + **archival storage** ("a read/write database storing arbitrary length text objects"). Paging is function-call driven and "**entirely self-directed**" (`request_heartbeat=true` chains calls). Eviction is **memory-pressure** driven: at a "warning token count" (~70%) the queue manager injects "a system message... warning the LLM of an impending queue eviction (a '**memory pressure**' warning)"; at the "flush token count" (100%) it evicts ~50% and "generates a new recursive summary," leaving evicted messages "stored indefinitely in recall storage" ([arXiv 2310.08560](https://arxiv.org/abs/2310.08560)). Letta's current tiers are **"Message Buffer: Recent Messages," "Core Memory: In-Context Memory Blocks"** ("remain **pinned** to the agent's context window"), **"Recall Memory: Conversational History,"** and **"Archival Memory: Explicitly Stored Knowledge"** — archival being "**Agent-immutable**," with blocks prompted verbatim as `<persona>` / `<human>` XML ([Letta](https://www.letta.com/blog/agent-memory/), [archival](https://docs.letta.com/v1-sdk/memory/archival-memory), [blocks](https://docs.letta.com/v1-sdk/memory/memory-blocks.md)). **Sleep-time compute** ([arXiv 2504.13171](https://arxiv.org/abs/2504.13171)) defines the offline/online split: "Letta actually creates **two agents**... a primary agent and a sleep-time agent... **the primary agent is not provided with tools to edit its core memory**... These tools are attached to the sleep-time agent," which writes "in an '**anytime**' fashion," because "Memory formation in MemGPT is incremental, so memories may become **messy and disorganized** over time" ([Letta](https://www.letta.com/blog/sleep-time-compute)).

**Mem0.** **Extraction** (LLM over a conversation summary, a 10-message recency window, and the new pair) → **update** (retrieve top-10 similar memories; an LLM function call picks the op) → retrieval. The op set is **`ADD`** ("creation of new memories when no semantically equivalent memory exists"), **`UPDATE`** ("augmentation of existing memories with complementary information"), **`DELETE`** ("removal of memories contradicted by new information"), **`NOOP`**. **Graph memory** stores "memories... as directed labeled graphs with entities as nodes and relationships as edges," marking conflicts "as invalid rather than physically removing them" ([arXiv 2504.19413](https://arxiv.org/abs/2504.19413)). **The product diverged from the paper:** docs now describe "**ADD-only** facts" ([How Mem0 Works](https://docs.mem0.ai/core-concepts/how-it-works.md)), and of its `MemoryType` enum "**only `procedural_memory` is a real, working value**" — semantic and episodic are "Not implemented" ([Memory Types](https://docs.mem0.ai/core-concepts/memory-types)).

**Zep / Graphiti.** Three **hierarchical tiers of subgraphs**: the **episode subgraph** ("Episodes serve as a **non-lossy** data store from which semantic entities and relations are extracted"), the **semantic entity subgraph** ("Entity nodes," "Entity edges (semantic edges)"), and the **community subgraph** (nodes holding "high-level summarizations"). The **bi-temporal model** tracks four timestamps: "`t'created` and `t'expired ∈ T'` monitor when facts are created or invalidated **in the system**, while `t_valid` and `t_invalid ∈ T` track the temporal range during which **facts held true**" — ingestion time versus valid time. Contradictions trigger **invalidation, not deletion**: "it **invalidates the affected edges by setting their `t_invalid` to the `t_valid` of the invalidating edge**" ([arXiv 2501.13956](https://arxiv.org/abs/2501.13956)). ⚠️ Docs and paper disagree on community detection: the paper uses "**label propagation**... rather than the Leiden algorithm," the docs say "**Leiden**."

**LangMem / LangGraph.** **Short-term memory** is "**thread-scoped memory**... maintaining message history within a session," persisted "using a **checkpointer**"; **long-term memory** "is shared *across* conversational threads" and lives in **stores** as JSON documents under a **namespace** + key ([LangGraph](https://docs.langchain.com/oss/python/langgraph/memory)). Types are CoALA-derived: "**semantic memory**" (patterns "**Profile**" / "**Collection**"), "**episodic memory**," "**procedural memory**." Writing is "**in the hot path**" (real-time, but reasoning about what to save "**can impact agent latency**" and the agent must "**multitask**") or "**in the background**" ("It **eliminates latency** in the primary application"); LangMem renames these "**Conscious Formation**" (adds "**perceptible latency**") and "**Subconscious Formation**" ([LangMem](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)). "**LangMem doesn't yet support opinionated utilities for episodic memory**" ([LangChain](https://www.langchain.com/blog/langmem-sdk-launch)). The **summarization node** (`langmem.short_term.SummarizationNode`, via `pre_model_hook`) replaces trimmed history with a rolling summary ([LangGraph docs](https://github.com/langchain-ai/langgraph/blob/f8c1a323cc50a6da14836ebc4c53c79db0f6508c/docs/docs/how-tos/memory/add-memory.md)).

**CoALA (reference vocabulary).** Working memory is "**a data structure that persists across LLM calls**"; "**episodic memory** stores experience from earlier decision cycles"; "**semantic memory** stores an agent's knowledge about the world and itself"; "**procedural memory**" comprises "**implicit knowledge stored in the LLM weights**, and **explicit knowledge written in the agent's code**" — writing to which is "significantly **riskier**" than writing to episodic or semantic memory. Its action split: **retrieval actions** "**read information from long-term memories into working memory**"; **reasoning actions** "**read from and write to working memory**"; **learning actions** are "**writing information to long-term memory**" ([arXiv 2309.02427](https://arxiv.org/abs/2309.02427)).

**Mapping and deviations.** [EXTRAPOLATION] LangGraph–LangMem is closest to CoALA's vocabulary (identical long-term names; LangGraph's docs cite CoALA directly). Working memory is roughly shared across all four (LangGraph thread state ≈ MemGPT main context ≈ Letta message buffer + core memory), but Letta splits it into a pinned model-editable block tier plus a rolling buffer and adds a fourth tier CoALA never names — **archival memory**. Mem0 implements only **procedural** of CoALA's three long-term types. Zep/Graphiti deviates most: episodic-vs-semantic is a *subgraph* distinction, and it alone has bi-temporal validity windows and invalidation-not-deletion. CoALA's retrieval/reasoning/learning triad has no documented counterpart in the other four.
