# Externalizing agent state: "the model is not the database"

**Thesis [EXTRAPOLATION]:** the mechanisms below converge on one split — an append-only, deterministic record is the source of truth; the model reads a *projection* of it and emits *proposals*, which a deterministic layer validates and commits. Anything the model authors (summaries, NOTES.md, memory files) is derived state and inherits derived-state risk.

---

## 1. Durable execution: state is the log, replay is a pure function

**Temporal.** The Event History is "**An append-only log of Events for your application**," durably persisted so "your application state survives crashes or failures," and it "also serves as an audit log for debugging" ([docs.temporal.io](https://docs.temporal.io/workflow-execution/event.md)). Workflow code never acts directly: it emits **Commands**, the Service maps them to **Events**, and on recovery "the Worker uses the Event History to replay the code and recreate the state of the Workflow Execution to what it was immediately before the crash" ([Event History](https://docs.temporal.io/encyclopedia/event-history/)). Replay is defined as "**During a Replay the Commands that are generated are checked against an existing Event History**"; a mismatch is a non-determinism error ([Workflow Execution](https://docs.temporal.io/workflow-execution.md)).

What is re-derived vs. not, concretely:
- **Re-derived:** control flow and local variables — "if the code tries to call a function… the framework consults the execution history… it replays that function's result" ([Azure Durable Orchestrations](https://learn.microsoft.com/en-us/azure/durable-task/common/durable-task-orchestrations), 2026-07-24).
- **Must NOT be re-derived — including LLM calls:** "To handle non-deterministic operations like API calls, **LLM/AI invocations**, database queries… put them in Activities. Activities execute outside the replay path" ([Temporal Workflow Definition](https://docs.temporal.io/workflow-definition.md)).
- **Time/UUID/randomness are memoized:** a `SideEffect` "executes the provided function **once and records its result into the Workflow Execution Event History**… does not re-execute upon replay, but instead returns the recorded result" ([Events](https://docs.temporal.io/workflow-execution/event.md)).
- **The log has a budget:** Temporal warns at 10,240 events and terminates at 51,200 events / 2,000 Updates / 10,000 Signals. **Continue-As-New** passes "the latest relevant state… with a fresh Event History" to a new Run with the same Workflow Id, letting Entity Workflows run forever ([Continue-As-New](https://docs.temporal.io/workflow-execution/continue-as-new.md)).

Temporal's AI page frames agents as "long-running, stateful agent loops… wait on humans, and pick up exactly where they left off," with Approval and Entity Workflow as canonical patterns ([docs.temporal.io/ai](https://docs.temporal.io/ai.md)). A guest post wraps *unmodified* LangGraph agents so that "Thread → Workflow instance… Checkpoint → Workflow state, persisted in history," keeping only the latest checkpoint because "Temporal's Workflow replay can restore an agent to any previous state" ([temporal.io/blog](https://temporal.io/blog/manetu-the-thread-is-the-workflow), Sep 3 2026). Temporal's MCP pitch: implement tools as Workflows so "tools continue progressing even if the MCP client or server crashes" ([Durable MCP](https://temporal.io/blog/durable-mcp-how-to-give-agentic-systems-superpowers), Jul 9 2025).

**Restate.** "Restate tracks every step of your code execution in a **journal**… it records both the operation and its result. If your function crashes or fails, Restate **replays the journal, skipping completed steps**." Virtual Objects are journaled K/V state with a **single-writer guarantee**, explicitly scoped to "**agent context and memory**" ([Key Concepts](https://docs.restate.dev/foundations/key-concepts.md)). The payoff, verbatim: "LLM calls are not repeated (saving cost and time); Tool side effects are not duplicated (no double bookings, no duplicate emails)" ([Durable Agents](https://docs.restate.dev/ai/patterns/durable-agents.md)). Its runtime comparison notes that checkpoint-style systems leave "side effects… [needing] explicit task boundaries and idempotency protection" ([What is an Agent Runtime?](https://restate.dev/what-is-an-agent-runtime), updated Jul 31 2026).

**DBOS** checkpoints to Postgres: "**one database write per step**… plus two additional database writes per workflow"; recovery re-invokes with checkpointed inputs, returns checkpointed outputs instead of re-executing, and resumes at the first uncheckpointed step. Requirements: workflow **deterministic**, steps **idempotent** — "once a step completes and is checkpointed, it is never re-executed." It advises "store large files in cloud blob storage like S3 and have steps return pointers" ([DBOS Architecture](https://docs.dbos.dev/architecture)).

**Inngest** names the trick: "**step-level memoization**… Non-deterministic code on the first run. Deterministic replay on recovery," because "the memoized results *force* the same path" ([Durable Agents](https://www.inngest.com/docs/learn/durable-agents)). **Azure Durable Task** says it outright: orchestrators "use the **event sourcing** design pattern… an append-only store to record the full series of actions," with a published history table (`ExecutionStarted`, `TaskScheduled`, `TaskCompleted`, `ExecutionCompleted`) ([Durable Orchestrations](https://learn.microsoft.com/en-us/azure/durable-task/common/durable-task-orchestrations)).

## 2. Filesystem as memory: context offloading, notes, indexes

Anthropic's context-engineering post (Sep 29 2025) states the pattern: agents keep "**lightweight identifiers (file paths, stored queries, web links, etc.)** and use these references to dynamically load data into context at runtime," enabling "**progressive disclosure**." It names **structured note-taking** ("your custom agent maintaining a NOTES.md file") alongside **compaction** and sub-agents, and warns "overly aggressive compaction can result in the loss of subtle but critical context whose importance only becomes apparent later" ([anthropic.com/engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).

The **memory tool** makes it an API primitive: files under `/memories`, executed **client-side** by your handler, for "just-in-time context retrieval." The API injects: "**ASSUME INTERRUPTION: Your context window might be reset at any moment, so you risk losing any progress that is not recorded in your memory directory**." The documented multisession pattern is an initializer session writing a **progress log** and **feature checklist**; later sessions resume from those files and update the log before exit ([Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool.md)); the cookbook pairs this with **context editing** (`clear_tool_uses_20250919`) to drop stale tool results ([cookbook](https://platform.claude.com/cookbook/tool-use-memory-cookbook)).

**Claude Code** ships it: `CLAUDE.md` files load at session start, target "**under 200 lines**," support `@path` imports, and "Project-root CLAUDE.md **survives compaction**: after `/compact`, Claude re-reads it from disk and re-injects it." **Auto memory** keeps a `MEMORY.md` **index** (first 200 lines / 25KB loaded each session) plus topic files "read on demand" ([code.claude.com/docs/en/memory](https://code.claude.com/docs/en/memory.md)).

**LangChain Deep Agents** (Jan 28 2026) gives thresholds: tool results over **20,000 tokens** are offloaded and replaced by "a file path reference and a preview of the first 10 lines"; large write/edit arguments are evicted at **85%** of the window; only then does summarization run — and "**the complete, original conversation messages are written to the filesystem as a canonical record**." Its evals check that a summarized-away fact is recoverable, and it flags "**goal drift**" as "the most insidious failure mode" ([langchain.com/blog](https://www.langchain.com/blog/context-management-for-deepagents)).

**Anthropic's long-running harness** (Nov 26 2025) adds the discipline that makes files trustworthy: an initializer writes `init.sh`, `claude-progress.txt`, and `feature_list.json` where agents may only flip `passes` flags ("It is unacceptable to remove or edit tests"); they chose JSON over Markdown because "the model is less likely to inappropriately change or overwrite JSON files" ([anthropic.com/engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). **Manus** (Jul 18 2025) contributes "Make your context **append-only**" for KV-cache stability, treats the file system as external memory, and re-reads a plan file to fight "lost-in-the-middle" ([manus.im/blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)).

**Caveat [EXTRAPOLATION]:** a scratchpad directory is *mutable derived state* — it has no append-only guarantee and no replay semantics of its own; mirrors of Manus's principles (e.g. [this paraphrase](https://raw.githubusercontent.com/galaxy-dawn/claude-scholar/refs/heads/main/skills/planning-with-files/reference.md)) are secondary sources.

## 3. Event sourcing + CQRS for agent memory and decision logs

The classical definitions are still the best specs. Fowler (2005): "**Event Sourcing** ensures that all changes to application state are stored as a sequence of events," enabling **Complete Rebuild**, **Temporal Query**, and **Event Replay**; and — an ancestor of memoized LLM calls — external queries during replay need a gateway that "remembers the responses to its queries and uses them during replay" ([martinfowler.com](https://martinfowler.com/eaaDev/EventSourcing.html)). The Azure Architecture Center (updated 2026-03-28) adds: the append-only store "serves as the system of record"; state is derived by **rehydration**; **materialized views** exist "because it's costly to read and replay events"; write **intent**, not just deltas, or the store becomes "a change log that has no business meaning"; **snapshots are an optimization, not a replacement**; and it warns that "Event sourcing is a complex pattern… For most systems… traditional data management is sufficient" ([Azure](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)).

Research is converging on the same question. **Generative Agents** (arXiv 2304.03442, 2023) stores "**a complete record of the agent's experiences using natural language**, synthesize[s] those memories over time into higher-level reflections, and retrieve[s] them dynamically" — reflection being exactly the derived layer that drifts ([arXiv](https://arxiv.org/abs/2304.03442)). **"Is Agent Memory a Database?"** (arXiv 2605.26252, May 2026) argues memory systems "treat memory as storage," localizing correctness "at records, embeddings, or edges," producing four failure modes (unregulated growth, missing semantic revision, capacity-driven forgetting, read-only retrieval), and proposes that "**correctness is a property of the state trajectory, not of individual records**" ([arXiv](https://arxiv.org/abs/2605.26252)). **TierMem** (arXiv 2602.17913, Feb 2026) names the anti-pattern: write-time summaries create a "**write-before-query barrier**" and "**unverifiable omissions**" (a dropped allergy), while "**Retaining raw logs restores an authoritative source of truth**"; it queries summaries by default but **escalates to an immutable raw-log store** when evidence is insufficient, writing findings back *linked to their raw sources* ([arXiv](https://arxiv.org/abs/2602.17913)).

For audit trails, a useful but **non-authoritative** artifact is the IETF individual Internet-Draft "Agent Audit Trail" (2026): hash-chained JSONL records with a mandatory taxonomy (`tool_call`, `decision`, `delegation`, `escalation`, `denied`/`escalated` outcomes), and a `record_phase` field distinguishing **pre-execution** from post-execution records so logs "prove policy enforcement, not merely observation" ([datatracker.ietf.org](https://datatracker.ietf.org/doc/draft-sharif-agent-audit-trail/01/)) — an I-D with "no formal standing," not a standard. **Skepticism:** engine-vs-engine comparison posts and "agent memory is not a database" landing pages are marketing-tier; the durable-execution vendors are also selling, but their docs specify shipped mechanics (journal formats, replay rules, limits) corroborated across four engines.

## 4. Idempotency, exactly-once, and letting the deterministic system dispose

- **Dedupe at the boundary.** Stripe's idempotency layer saves "the resulting status code and body of the first request… regardless of whether it succeeds or fails," returns the same result for repeated keys (**including 500s**), errors if a key is reused with different parameters, and prunes keys after ~24h ([Stripe](https://docs.stripe.com/api/idempotent_requests)). Restate dedupes via idempotency keys ([Key Concepts](https://docs.restate.dev/foundations/key-concepts.md)).
- **Exactly-once is partial by design.** Temporal dedupes **Updates** server-side by Update ID, but "For **Signals**, you should use a custom idempotency key… implementing the deduplication in your Workflow code," and Update-ID dedup is per-run, so Continue-As-New needs app-level dedup ([Handling Messages](https://docs.temporal.io/handling-messages.md)).
- **Pre-commit validation is a hook.** Temporal **Update Validators** are "a read operation that's responsible for **accepting or rejecting** the Update"; on rejection "the Workflow will have no indication that it was ever requested" ([Handling Messages](https://docs.temporal.io/handling-messages.md)). That is the clean shape for "the agent proposes, the deterministic system disposes."
- **Human approval as a log event.** Temporal's Approval pattern blocks on a Signal carrying structured `ApprovalData` (approver, decision, comments, timestamp), times out and escalates, and notes "**All approval data is recorded in the Workflow history as Signal events, giving you a built-in audit trail**" — with the explicit warning to "**Ensure idempotency**… Signals may be duplicated" ([Approval Pattern](https://docs.temporal.io/design-patterns/approval.md)).
- **Idempotency is what keeps projections honest.** Azure: "Event delivery to consumers is typically *at least once*… Event handlers must be **idempotent**… **Without idempotency, projections drift from the event stream** and side effects such as payments or notifications trigger more than once" ([Azure](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)). One sentence links §3's derived-state drift to §4's retry semantics.
- **Instruction ≠ enforcement.** Claude Code's docs draw the line the pattern depends on: "Settings rules are enforced by the client regardless of what Claude decides. **CLAUDE.md instructions shape Claude's behavior but are not a hard enforcement layer**" ([memory docs](https://code.claude.com/docs/en/memory.md)); Anthropic separately recommends guardrails via separate screening calls and sandboxed testing ([Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents), Dec 19 2024).

**Bottom line [EXTRAPOLATION]:** put the event log in the authority position; treat every model-authored artifact — summary, NOTES.md, MEMORY.md, retrieved "memory" — as a *cache with provenance*, rebuildable from raw records (TierMem's escalation rule is the right default); memoize every LLM/tool call as a journal entry so replay stays pure; route irreversible actions through an idempotency key plus a validator/approval gate enforced outside the model; and bound the log deliberately (Continue-As-New-style checkpoints, pointer-not-payload steps), because append-only histories grow forever by construction.
