# dsh-trader 操作台（Trade Console）架构设计

> 状态：**S0 Web 启动/挂载、S1 启动恢复投影、S2 client 状态消费已验证；浏览器视觉确认仍待做**（v4，2026-09-18）
> v3 的修订动因（来自澄清）：① 交易 agent **可能不再有"会话"概念** ⇒ 组织单位必须换；② 重启后数据可信度**本就下降** ⇒ 不假装持久真相，改为可信度标注；③ 形态确认为**同进程**、DSH 是交易 docker 主进程、`restart: unless-stopped` 保活 ⇒ 生存性靠"启动能正确重建且不死锁"，不靠第二个进程；④ 主要风险变成**信息源多且异质导致杂乱** ⇒ 必须给出整合规则。

当前实现：`dsh-trader` 已声明 `dsh.client` 与 `exports["./client"]`，构建产物为 DSH
`window.__ModuleLoader__.load(...)` bundle；client 注册 `main` 与
`sidebar.panellist` 两个只读座位，轮询状态与周期 GET 投影，不调用 `connection`、不提供
交易控制操作。
`scripts/client-s0-check.mjs` 可在无浏览器/无网络条件下验证 bundle 形状、注入面和座位注册；
服务端已注册只读 `GET /api/trade/state` 与 `GET /api/trade/cycles`：通过 DSH authenticated connection 读取当前
TradePorts 的账户/持仓/挂单与持久化 `halted`；runtime 启动过程追加到已有
`audit_events`，状态接口同时投影当前步骤、失败原文、uptime 和近 1h/24h 启动次数，
所以 runtime 尚未就绪时也能返回 503 + 启动恢复信息；没有 POST、撤单、模式切换或其它
控制路径。周期台账 v0 以 `decisions.decision_id` 为周期根，通过已有外键/哈希关联计划、
上下文、订单、成交、结算、教训和精确匹配的审计事件；没有显式关联的事件不强行归入。
真正启动 `trade` profile 查看原生外壳与座位仍是
S0 的未完成验收。

## 1. 前提与约束

| # | 前提 | 架构含义 |
|---|---|---|
| P1 | UI 是**交易 profile 自己的 Web 面**（同进程，形似 DSH 常规 coding agent 预设，但**展示的内容结构不同、服务端复杂度明显更高**） | 外壳与机制复用；**复杂度预算放在服务端**，客户端保持薄 |
| P2 | DSH 是交易 docker 的**主进程**，`restart: unless-stopped` 保活 | 不引入 systemd、不引入第二个监控进程；但**崩溃循环会被 restart 政策藏起来** ⇒ 必须可见化 |
| P3 | 运行期数据可信度：**交易所才是真相**；重启后交易进程本就会重新全量获取官方数据；**只要进程死过，本地数据可信度一律下降** | UI 不承担"保存真相"的职责，承担**标注可信度**的职责 |
| P4 | 交易 agent **可能没有会话概念**（唤醒→审议→裁决→计划卡，而不是一段对话） | **"会话"不能作为界面的组织单位**；消息与工具调用需要新的归属键 |
| P5 | 7×24；判断只在 W1/W2/W3 窗口内发生；写操作只有代码里的硬闸与 kill switch | 红线：硬闸不可绕过、密钥不进 UI、pm 只读、审计优先、**失败逐字保留** |
| P6 | 信息源异质且多：交易所有两个方向（公共行情 / 私有账户）、本地审计账本、**六类上下文（C1–C6）与四层记忆（M0–M3）**、多 agent 消息与工具调用、对账、成本 | 必须有**单一挂载点**与**防杂乱规则**（§3） |

## 2. 架构判断

1. **复用能力，自建组织单位。** 复用 DSH 的外壳、座位机制、命令、设置、主题/i18n，以及**消息与工具调用的渲染能力**；**不复用"会话"作为组织单位**——交易世界里的组织单位是**周期**。
2. **单挂载点。** 任何信息只能挂到两类对象之一：**周期（Cycle）** 或 **当前状态（State）**。没有第三类页面。这是"不杂乱"的结构性保证，而不是靠设计感。
3. **可信度是一等公民。** 每个数字带 `source + asOf + credibility`。重启后 exchange 类读数降级为 `unknown/stale`，UI 直接显示"重建中"，而不是把旧数当新数。
4. **服务端厚、客户端薄。** 聚合、判定、可信度、告警推导全在服务端；客户端只做导航与呈现 ⇒ 一份口径，且客户端无从产生"另一个数"。
5. **启动重建是一等对象。** 冷启动序列、每步结果与失败原因、启动计数、uptime 都要能在界面上看到——因为 `restart: unless-stopped` 会让"每 20 秒崩一次"表现成"服务一直在跑"。
6. **写操作只有一个**：暂停/恢复，且复用既有命令的同一实现。其余写能力在架构上**不留通道**（不是"暂缓"）。

## 3. 信息模型：为什么不会杂乱

### 3.1 唯一的组织单位：交易周期（Cycle）

**定义**：从一次唤醒窗口开始，到该窗口产出的决策被结算（或明确 deferred）为止的完整生命周期。

```text
窗口开启 → 证据组装 → 审议 → 裁决 → 计划卡 → 执行 → 结算 → 教训/归档
（W1/W2/W3）  （C1–C6）  （多 agent）  （硬闸）  （承诺）  （订单）  （外部）  （M2/M3）
```

**为什么用周期**：它天然把八类异质来源收进**同一条时间线**，并且给每个来源一个**固定座位**。于是界面不需要"按数据源分页"，也不需要"每类信息一个仪表盘"——这正是杂乱的来源。

**顺带解决一个 7×24 问题**：若沿用"一个长驻会话"，投研与执行记录会无限增长成一条不可读的流。以周期为单位，天然分段、天然可归档。

### 3.2 挂载表（信息源 → 座位）

| 信息源 | 挂在周期的哪一段 | 展示口径 |
|---|---|---|
| 唤醒窗口与触发（`windows`/`triggers`，含被冷却/限流压掉的） | **起点** | 为什么这个周期存在 |
| **上下文快照（C1–C6）**：`context_snapshots` 的 `part_hashes` / `changed_parts` / `char_counts` / `overflow` | **证据** | "模型实际看到了什么"——含**被遮蔽项清单**（遮蔽而非删除） |
| 记忆检索（C5 recall：被检索到的 M2 决策/M3 教训切片） | **证据** | 检索依据（regime 相似度、时间近邻），以及**反方教训** |
| 市场与指标（`bars`/`features`/衍生品/预测市场） | **证据** | **只展示被引用到的那些**，不铺全量；C6 标注"永不入上下文，按需工具取" |
| 多 agent 消息与工具调用（desk / L1 / L2 / L3 / 分析师 / 多空辩论 / 风控 / 裁决） | **审议** | 按周期归集；工具调用只展示**落到交易语义上的**（报价、风险检查、下单一类的输入输出） |
| 硬闸裁决（`gate` 结果 + `execute.denied` 审计原文） | **裁决** | 逐字保留拒绝原因 |
| 候选/激活计划卡（`when`/`then`/失效/承诺） | **裁决 → 执行** | DSL 原文 + 人类可读摘要 |
| 意图/订单/成交（`order_intents`/`orders`/`fills`） | **执行** | 含 `unknown` 态（fail-closed 冻结） |
| 对账差异（P0/P1 分类） | **执行 → 结算之间** | 本地与交易所的分歧 |
| 结算（`outcomes`：净收益、alpha、MFE/MAE、是否止损、`deferred`） | **结算** | 分母必须 > 0 才谈比率 |
| 教训（`lessons` + 证据指针 + TTL + regime 桶） | **收尾** | 只读；写入需人审（M3 纪律） |
| 模型成本（token/耗时/费用/`cost_known`） | **周期贴纸** | 每次模型调用一行 |

### 3.3 另一类对象：当前状态（State）

不属于任何周期、只描述"现在"的东西：账户权益、持仓、挂单、保护单、风控余量、心跳与熔断、模式（`paper`/`live_auto`）、数据源健康、价目新鲜度、今日预算与唤醒频率、下次窗口倒计时。

**状态面与周期面共用同一份读模型**，因此不会出现"两个看板两个数"。

### 3.4 可信度模型（P3 的落点）

| 级别 | 含义 | UI 表现 |
|---|---|---|
| `exchange-live` | 本次刷新从交易所直读成功 | 正常 |
| `exchange-stale` | 有读数，但超出新鲜度阈值，或**重启后尚未重取** | 黄标 + 显式 `asOf` |
| `local-audit` | 本地 append-only 账本（审计级可信，描述历史） | 正常（历史事实） |
| `derived` | 由上述推导（余量、比率、告警） | 标注推导口径 |
| `unknown` | 读失败 / 尚未初始化 | `—` + **原样错误**；**绝不显示 0** |

**关键规则**：进程重启 → 整机进入**"正在重建"**状态，所有 `exchange-*` 降级为 `unknown/stale`，直到重建完成才恢复。**不允许出现"看起来还在跑"的假象。**

### 3.5 三条防杂乱规则（可检查）

1. **单一主座位**：每个信息源在界面里只有一个主座位（§3.2 定死）；其它出现只能是引用或下钻。
2. **可下钻**：任何聚合数字必须能一键点到原始行（周期/决策/订单/审计 `seq`）。
3. **一屏一问**：一屏只回答一个问题；跨源聚合只允许出现在**周期详情**与**当前状态**两处。

## 4. 系统架构

### 4.1 分层与复杂度预算

```text
┌ 运行时 ────────────────────────────────────────────────────────────────┐
│ DSH 主进程（交易 docker PID1，restart: unless-stopped）                  │
├ 复用层（设计可复用，部分需按交易语义调整）─────────────────────────────┤
│ 外壳：布局 / 左栏 / 中央面板 / 右栏 / 浮层 / 设置 / 主题 / i18n            │
│ 机制：唤醒调度 · agent 回合 · 工具调用 · 子 agent · 命令                  │
│ 渲染能力：消息流 · 工具调用卡片 · 时间轴（**复用的是渲染能力，不是"会话"这个单位**）│
├ 交易服务层（★ 复杂度集中在这里）────────────────────────────────────────┤
│ ① 读模型：周期投影 / 状态投影（纯函数 + 注入时钟）                        │
│ ② 可信度与新鲜度判定（§3.4）                                             │
│ ③ 上下文装配解释器（把 context_snapshots 的哈希/变更/遮蔽还原成可读结构） │
│ ④ 消息归集（把多 agent 消息与工具调用绑到周期键上）                       │
│ ⑤ 启动重建状态机（§4.3）                                                 │
│ ⑥ 告警推导（P0/P1/P2）                                                   │
│ ⑦ 取数端点（只读）+ 控制端点（仅暂停/恢复）                               │
├ 呈现层（薄）────────────────────────────────────────────────────────────┤
│ 座位注册 + 导航 + 表格/时间轴/卡片渲染 + 轻交互；无业务判定                │
└ 持久化（已有）──────────────────────────────────────────────────────────┤
  audit_events(append-only) · decisions · plan_cards · order_intents · orders ·
  fills · outcomes · lessons · triggers · budget_ledger · heartbeat · price_table ·
  context_snapshots · config_versions
```

### 4.2 数据流

```text
交易所（公共行情 / 私有账户只读）──┐
                                  ├─► 交易服务层 ① 投影 ──► 周期面 / 状态面
本地账本（上表全部）──────────────┤            ②③④⑤⑥
多 agent 消息与工具调用 ──────────┘                 │
                                             ⑦ 只读端点（带可信度）
                                                   │
                              客户端座位渲染 ◄──────┘
                                    │
                                    └─► 控制端点（仅暂停/恢复，复用既有命令实现，双向审计）
```

### 4.3 启动与重建（新增的一等对象）

序列（每一步都有状态、耗时、失败原因、是否阻塞）：

```text
boot → DB 可用性与迁移 → 交易所连通性（只读） → 权威状态重取（权益/持仓/挂单）
     → 对账（本地镜像 vs 交易所） → 调度游标恢复（不重复触发、不漏触发）
     → 未完成意图处置（created/acked → 判 unknown 并冻结）
     → ready
```

UI 必须显示：当前处于哪一步、失败原因（原样）、`boot_at` / `uptime` / **近 1h 与 24h 的启动次数** / 上次启动的失败原因。

**理由**：`restart: unless-stopped` 会把"异常死锁→崩溃→重启"表现成"服务一直活着"。让启动次数与失败原因可见，是这条保活策略下**唯一**能发现循环故障的手段。这也是 P3"进程死过则可信度下降"在界面上的落点。

## 5. 界面结构（内容结构，不是像素）

### 5.1 主导航

| 导航项 | 回答的问题 | 对象 |
|---|---|---|
| **当前状态**（默认落点） | 现在能不能交易？手上有什么？出事了没？ | State |
| **周期台账** | 到目前为止它做过哪些判断？结果如何？ | Cycle 列表 |
| **周期详情** | 这一个周期里发生了什么、为什么这么判？ | 单个 Cycle |
| **执行与持仓** | 意图→订单→成交→保护单的链路对不对？ | State（专门视图） |
| **审计与事件** | 谁在什么时候做了什么？（含系统与人工） | 横切流 |
| **成本与预算** | 今天花了多少？成本可信吗？ | 横切 |
| **系统与启动** | 重建成功了吗？有没有在崩溃循环？数据源健康吗？ | 横切 |
| **设置** | 生效参数是什么？（复用原生设置页 + 只读交易参数节） | 复用 + 只读 |

### 5.2 周期详情的分区（不是聊天流）

按 §3.2 的八段纵向排布；**"审议"段的内部**才是消息与工具调用，容器是周期而不是会话：

```text
[起点] 触发与窗口（含被压掉的原因）
[证据] 上下文快照 C1–C6（哈希/变更/字符数/遮蔽清单）· 记忆检索切片 · 被引用的行情与指标
[审议] L1/L2/L3 与多空/风控/裁决的消息与工具调用（按角色分组，默认折叠）
[裁决] 硬闸结论 + 拒绝原文（若有）
[计划] 计划卡（DSL 原文 + 摘要 + 失效条件 + 承诺）
[执行] 意图/订单/成交/保护单（含 unknown 冻结）
[结算] 净收益 · alpha · MFE/MAE · 是否止损 · deferred
[收尾] 教训 + 证据指针 + TTL
```

### 5.3 哪些是"复用"，哪些必须"调整"

| 方面 | 复用 | 需调整/自建 |
|---|---|---|
| 外壳、座位、设置、主题、i18n、命令 | ✅ | 只注册座位（`main` 用我们自己的 key；可不动原生布局） |
| 消息渲染、工具调用卡片、时间轴 | ✅ 能力复用 | **容器换成周期**；工具卡片增加交易语义（下单/拒单/成交/保护单） |
| **组织单位** | ❌ | **会话 → 周期**（这是最大的一处改动，也是 P4 的直接后果） |
| 消息归属键 | ❌ | 若 agent 无会话：消息/工具调用需要 `cycle` 键（唤醒时打标；否则无法归集） |
| 周期标题 | — | 可直接用唤醒的 `notice.summary`（≤120 字符硬上限），无需新生成 |
| 服务端 | ❌ | 读模型、可信度、上下文解释、归集、重建状态机、告警（§4.1 的 ①–⑦） |

### 5.4 人机交互面（P4 带来的新问题）

若交易 agent 真的没有会话，操作员的"表达"通道需要重新定义。三个候选：

| 候选 | 评价 |
|---|---|
| **命令**（`/halt`、`/resume`） | 必须有；但只能表达少数几个动作 |
| **审计化的"操作备注"**（写入后成为下一周期上下文的一部分，带作者与时间，可被模型看到） | **推荐**：它真正进入决策回路，且完全可审计 |
| 保留一个"纯运维会话"（与交易回路解耦，只用于人机对话） | 好处是熟悉；坏处是容易变成"聊天不产生后果"的剧场，且又会引入会话概念 |

## 6. 关键架构决策（ADR）

| # | 决策 | 理由 | 被否选项 |
|---|---|---|---|
| **ADR-1** | UI = 该 profile 的 Web 面，**同进程** | P1；R1（agent 上下文与工具调用）只有同进程能完整满足；复杂度留在服务端 | 独立前端应用（要重写渲染层）；第二监控进程（P2 下无必要） |
| **ADR-2** | 只**加座位**，不覆盖已被占用的座位 | 只依赖最稳定的 ctx 能力；外壳升级不破坏我们 | 覆盖 `sidebar`/`main` 等 single 座位（会让原生导航消失）；依赖本地未安装的 UI 组件库 |
| **ADR-3** | **不以"落库快照"承担当前真相**；交易所是真相，重启即重取。落库只作为**可选**的历史/审计增强 | P3：重启后本就应当从交易所重建；进程死过则本地可信度下降，落库也救不回"当前真相" | 把账户/持仓快照当权威（会在重启后制造"看起来有数据"的假象）；让监控面自己去打交易所（凭据扩散） |
| **ADR-4** | 信息架构以**周期**为唯一组织单位，状态面为唯一另一类对象 | §3；从结构上消灭"按数据源分页"的杂乱 | 按数据源分页面；按 agent 分页面；以会话为中心 |
| **ADR-5** | 取数：**只读投影 + 轮询**；单进程单连接，无 WAL 需求 | 动作是分钟级；单进程无跨进程读问题 | 自建 SSE/WS（协议/重连/背压自扛）；滥用会话帧（越界）；为无收益的场景先开 WAL |
| **ADR-6** | **零新增 LLM 调用**：简报 = 既有消息与上下文的投影 | 红线 7：能由条件与逻辑得出的，不加模型调用 | 让模型写"今日总结"（花钱且会与账本口径分叉） |
| **ADR-7** | 控制面**只有暂停/恢复** | 红线 2/6：UI 不能成为绕过硬闸的通道；kill switch 只有一个实现 | UI 下单/撤单/改限额/切模式 |
| **ADR-8** | **启动重建与崩溃循环可见化**（启动计数、失败原因、重建进度） | P2：`restart: unless-stopped` 会藏起崩溃循环；这是保活策略下唯一的发现手段 | 只依赖 docker 的健康检查；靠日志（没人看） |
| **ADR-9** | 客户端薄、服务端厚 | 一份口径；客户端无从制造"第二个数" | 客户端自取数、自推导（口径必然分叉） |
